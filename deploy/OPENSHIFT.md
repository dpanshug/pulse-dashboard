# OSAIPO Pulse Dashboard deployment

The dashboard is deployed to the Osaipo E1 production cluster through Argo CD.
This repository owns application code, images, and the OpenShift overlay;
`osaipo/pulse-gitops` owns the tenant namespace and Argo CD Application.

## Delivery flow

1. Merge code to `main` in this repository.
2. GitHub Actions runs lint, tests, build, validation, and image publication.
3. The image workflow updates the immutable image tag on `main`.
4. Argo CD watches the production overlay at `main`.
5. Argo CD syncs the dashboard namespace and workloads.
6. Verify the Application, Deployments, Services, Routes, and health endpoint.

Do not routinely use `oc apply` or `kubectl apply` for application changes.
Use GitHub Actions and Argo CD. Direct cluster access is reserved for read-only
verification and one-time secret bootstrap.

## Required secrets

Secret values must never be committed to either repository. The following
runtime secrets are consumed by the core deployment:

- `frontend-proxy-cookie` with key `session_secret` — required for OAuth proxy;
- `frontend-proxy-tls` — generated by the OpenShift service CA annotation;
- `team-tracker-secrets` — optional Jira/GitHub/GitLab credentials;
- `osaipo-pulse-secrets` — optional OSAIPO integration credentials;
- `google-sa-key` — optional Google Sheets roster credential.

After the tenant namespace exists, create the OAuth cookie secret once through
an approved secret-management process, for example:

```bash
oc create secret generic frontend-proxy-cookie \
  -n osaipo-aspen--pulse-dashboard \
  --from-literal=session_secret="$(openssl rand -base64 32)"
```

Credential-bearing secrets should be created through the approved enterprise
secret-management process, not copied from a developer workstation.
